# Systems & Standard Operating Procedures (SOPs)

## Purpose
To provide a framework for documenting and standardizing business processes to ensure consistency, efficiency, and scalability.

## Core Philosophy

> "System is the rail line; without it, the train derails every time."

## Principles

### 1. Document Everything
- Policies for recruitment, procurement, sales, finance, production
- If it's not written down, it doesn't exist
- Documentation preserves institutional knowledge

### 2. Make It Repeatable
- Any trained person should execute to the same standard
- Consistency is the foundation of quality
- Repeatable processes enable delegation and scale

### 3. Update Regularly
- Systems evolve; review and upgrade periodically
- Stale systems are worse than no systems
- Schedule quarterly reviews of all SOPs

### 4. Use Technology
- ERP systems, shared dashboards for real-time information flow
- Automate where possible; document where not
- AI can automate parts of SOPs (data entry, scheduling, reporting)

### 5. Train and Enforce
- A system without training is just a document
- Monitor compliance and output
- Reward adherence; address violations consistently

### 6. Document with Purpose, Not Perfection
- Not every task needs a full SOP
- Use the 80/20 rule — only document the critical 20% that truly benefit from step-by-step instructions
- The rest can be handled by clear responsibilities (What/Who) and cadence (When)

### 7. Write, Don't Record
- Written documentation is easier to update, search, and maintain than videos
- Avoid the "documentation graveyard" — keep it lightweight and living
- Videos are hard to update and impossible to search

### 8. Feedback Loops Are Essential
- Include steps like "revise this template" or "add an FAQ" to continuously improve
- Make improvement part of the process, not an afterthought
- When something goes wrong, add a preventative step to prevent recurrence

### 9. Process Maps Are the Visual Companion
- A process map is a flowchart of how a process is done within an organisation
- It includes inputs, outputs, stakeholders, decisions, and order
- Visual maps are easier to understand, collaborate on, and update than text-only documents
- They serve as a "blueprint" before building detailed SOPs

### 10. Build the Map First, Then the SOP
- Process Map = high-level visual overview (What, Who, When)
- SOP = detailed step-by-step instructions (How)
- Checklist = quick verification of critical steps
- Rule of thumb: Build the map first, then write the SOP for the critical 20%

### 11. The "Keep Notes" System
- During each project, maintain a running log of what went wrong and what could be better
- This is your raw material for improvement
- Review at the end of each project (retrospective)
- Implement changes before the next project
- Small tweaks first; big changes after 5+ reps

### 12. Phased Documentation Approach
- **Phase 0 (New/Pilot):** No documentation yet — just validate product-market fit
- **Phase 1 (Early):** Document only what's proven necessary (critical 20%)
- **Phase 2 (Mature):** Document everything (if needed)
- **Phase 3 (Optimise):** Systems champion drives continuous improvement

## Decision Frameworks

### The 5-Step Systemization Framework

```
Step 1: WHAT — List every area of responsibility (granular actions)
Step 2: WHO — Assign to roles (not names) for scalability
Step 3: WHERE — Store everything in one work management tool
Step 4: WHEN — Define cadence, deadlines, recurring rhythms
Step 5: HOW — Create SOPs for the critical 20% only

FOUNDER-LED: Steps 1-2 (What/Who)
TEAM-LED: Steps 3-5 (Where/When/How)
```

### SOP Development Process

```
Step 1: IDENTIFY CORE ACTIVITIES
│
├── What are the 5-10 things that MUST happen for the business to run?
├── What happens if this step fails? (Impact assessment)
└── Who currently does this? (Owner identification)

Step 2: WRITE STEP-BY-STEP PROCEDURES
│
├── Start with the end (what should the output look like?)
├── Work backwards to the first step
├── Include decision points (if X, then Y)
└── Add quality checkpoints

Step 3: TRAIN ALL STAFF
│
├── Walk through the SOP with each person
├── Have them demonstrate the process
├── Document questions and gaps
└── Update SOP based on feedback

Step 4: MONITOR COMPLIANCE
│
├── Regular audits (weekly, monthly)
├── Output quality metrics
├── Exception tracking
└── Feedback loops

Step 5: REVISE AND IMPROVE
│
├── Quarterly SOP review
├── Incorporate feedback
├── Update for changing conditions
└── Version control
```

## Rules

- **Always document before you delegate** — undocumented processes create chaos
- **Always train on the SOP** — a document without training is just paper
- **Always version control** — track changes and review dates
- **Always have an owner** — every SOP needs a responsible person
- **Never assume people know** — explicit instruction prevents errors
- **Never skip the review cycle** — stale systems fail
- **Never record videos for documentation** — write instead
- **Never impose systems on your team** — co-create for adoption

## Heuristics

- If one person leaves and the process breaks, you don't have a system
- If you can't explain it in 5 steps, you don't understand it well enough
- If you're doing it differently every time, you need an SOP
- If you can't train someone in a week, the SOP is too complex
- If it's not written down, it doesn't exist
- If adoption is low, the system was imposed, not co-created
- Only the critical 20% of tasks need detailed SOPs

## Templates

### SOP Template

```
SOP TITLE: _______________
VERSION: ___
OWNER: ___
LAST REVIEWED: ___
NEXT REVIEW: ___

1. PURPOSE
   What is this SOP for?

2. SCOPE
   Who does this apply to?

3. RESPONSIBILITIES
   Who does what?

4. PROCEDURE
   Step 1: _______________
   Step 2: _______________
   Step 3: _______________
   [Decision points clearly marked]

5. QUALITY CHECKPOINTS
   How do we verify this was done correctly?

6. EXCEPTIONS
   What to do when the standard process doesn't work?

7. REVISION HISTORY
   Version | Date | Changes | Author
```

### Process Documentation Checklist

```
□ Process name and purpose defined
□ Start and end points clear
□ All steps documented in sequence
□ Decision points identified
□ Responsible person assigned
□ Quality checkpoints defined
□ Exceptions documented
□ Training materials created
□ Staff trained and tested
□ Compliance monitoring in place
```
